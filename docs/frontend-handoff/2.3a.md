# Frontend handoff: 2.3a sealed secrets console UX

Backend landed. The control plane seals, stores, pins, and delivers sealed
service secrets; the console has no UI for them yet. This doc is the contract
for that UI. It also covers the console remainder of parked
[1.2](../todo/freeze.md#12-encrypted-sealed-secrets).

## What the backend does (no console work needed)

- `ServiceRuntime.env` stays public configuration, stored in plaintext
  revision JSON exactly as before.
- Sealed secrets live in `service_secret_versions` (ciphertext) with
  per-environment DEKs wrapped by the envelope key provider. Values are
  write-only: no read API returns them.
- Names are disjoint from public env keys in both directions, validated as
  `[A-Za-z_][A-Za-z0-9_]*` (1–128 chars), with the `PLATFORM_` prefix
  reserved for platform-injected variables.
- Deployments capture sealed name-to-version pins in the dedicated
  `DeploymentRecord.sealed_versions` map (mapped to `sealedVersions`),
  kept separate from `variable_versions` (public env keys to spec
  revision) so a name that moves between public and sealed can never
  collide. Rollback restores the pinned values; the console only
  displays them.
- Desired-state assembly decrypts on the control plane for assigned
  allocations only. Duplicated environments never inherit sealed values,
  even with copy-variables enabled.

## API contract (all on PlatformService, Connect + gRPC)

Regenerate TS bindings with `bun run generate:proto`; the new methods
appear on the generated `PlatformService` client
(`#/lib/platform-gen/platform_pb`) used via
`console/src/lib/platform-grpc/client.server.ts`.

### SealServiceSecret — write-only create/update

Request: `{ service_id: string, name: string, value: string }`.
Response: `{ service_id, name, version: int64 }` (new version number).

- Each call appends an immutable version; re-sealing a deleted name
  resurrects it at a new version.
- Values are capped at 64 KiB; larger values fail fast.
- Errors: `InvalidArgument` (bad name, empty service id, oversize
  value — the message carries the limit, never the value),
  `FailedPrecondition` (name collides with a public env key — message
  names it; sealed backend unavailable),
  `PermissionDenied`/`NotFound` (access), `Unavailable`/`FailedPrecondition`
  (live-owner redirect, same handling as other mutations).

### ListServiceSecrets — masked existence

Request: `{ service_id: string }`.
Response: `{ secrets: [{ name, version: int64, updated_at }] }`, live names
only, ordered by name. Values are never present.

### DeleteServiceSecret — explicit deletion

Request: `{ service_id: string, name: string }`. Returns empty.
`NotFound` when the name has no sealed versions. Pinned deployment reads
keep resolving captured versions after deletion (rollback still works);
only current resolution drops the name.

## Console work items

1. Service settings environment section: split public variables (existing
   editor) from a sealed-secrets subsection. Sealed rows show name, version,
   and updated time with masked values that cannot be revealed, copied, or
   exported. Provide write-only create/update (never pre-fill the value
   field) and explicit delete with confirmation.
2. Follow the existing `*FromSession` pattern: add
   `sealServiceSecretFromSession` / `listServiceSecretsFromSession` /
   `deleteServiceSecretFromSession` in `console/src/lib/dashboard/server.ts`
   (or the services domain module it delegates to), thin server-fns in
   `console/src/routes/-dashboard/server-fns.ts`, and zod input validation
   mirroring the backend name rules.
3. Name-conflict UX: when sealing a name that exists as a public variable
   (or adding a public variable matching a sealed name), surface the
   backend `FailedPrecondition` message and guide the user to delete one
   side first. The backend enforces disjointness; the console must not let
   a user silently believe both exist.
4. Deployment details: `sealedVersions` already reaches the console;
   label those entries as pinned secret versions so rollback displays
   which secret versions a deployment captured. Never display values.
   (`variableVersions` carries public keys only and needs no
   cross-referencing.)
5. Never log, cache in readable stores, or include sealed values in loader
   data, error toasts, or test snapshots. Values travel from the input
   field to the seal RPC and nowhere else.

## Acceptance criteria

- A user can seal `TOKEN`, sees exactly one masked row (name, version 1),
  cannot read the value back through any console surface, and a second
  seal bumps the row to version 2.
- Sealing a name present in public env (and vice versa) shows an
  actionable conflict error; no state changes on either side.
- Deleting a sealed secret removes the row; rolling back to a deployment
  that captured it still delivers the captured value to the workload
  (verify via workload behavior, not by reading the value).
- Duplicating an environment with copy-variables copies public variables
  and zero sealed rows.
- `bun run check`, `typecheck`, unit, and integration suites pass; no
  secret value appears in console logs, snapshots, or fixtures.
