# Frontend handoff — 2.1 Durable-work package

Backend-only delivery. The durable-work queue, the migrated source caller,
and the dead-letter query API are implemented and tested. No console UI was
added or changed.

## Backend delivered

- `internal/controlplane/durablework`: CockroachDB-backed work queue
  (`durable_work_items`). States `pending/leased/succeeded/failed/dead`,
  owner-epoch fencing, lease expiry with heartbeat, bounded jittered retry.
- Source background work (`source_spec_changed`, `provider_access_changed`,
  `revision_observed`) now runs on the shared table. The bespoke
  `source_work_items` table is deleted. `github_webhook_deliveries` and
  `github_work_items` are untouched and migrate when next touched.
- Terminal rows are retained (previously completed source work was deleted),
  so dead and failed work is inspectable after the fact.

## Deferred UI: dead-letter inspection view

Operators need a read-only view of dead and failed work plus a re-enqueue
action. Suggested placement: an operator/support surface, not the per-service
views (follow the 3.10 operator control room when it lands; until then this
view has no home and stays unbuilt).

Proposed view contents per record:

- kind, state (`dead`/`failed`), dedup key
- resource identity (`resource_type`/`resource_id`), e.g. `service/<id>`,
  `github_installation/<id>`, `github_repository/<id>`
- attempt count/limit, owner, last error (already sanitized server-side),
  available-at, created/updated/completed timestamps
- payload summary (source payload: service, tracked ref, commit)

Proposed action: "re-enqueue" — re-enqueues the record's dedup key, which
resets a terminal record to pending (backend behavior already implemented).

## API contracts (backend)

Go API available today (`internal/controlplane/durablework`):

- `ListDead(ctx, kind, limit) ([]Record, error)` — dead records, newest
  first, optional kind filter, limit capped at 1000.
- `Get(ctx, id) (Record, error)` — one record by ID (`sql.ErrNoRows`
  when missing).
- `QueueLag(ctx, kinds...) (time.Duration, error)` — age of the oldest
  due pending record; export as the `durable_work_queue_lag_seconds` gauge.

`Record` fields: `ID, Kind, DedupKey, ResourceType, ResourceID, State,
AttemptCount, AttemptLimit, OwnerID, OwnerEpoch, LeaseExpiresAt
(sql.NullTime), LastError, AvailableAt, Payload (JSON bytes), CreatedAt,
UpdatedAt, CompletedAt (sql.NullTime)`.

Source payload shape (`internal/controlplane/source.WorkPayload`, JSON):

- `service_id, spec_revision, provider,
  provider_repository_external_id, provider_scope_external_id, tracked_ref,
  commit_sha, commit_message, commit_author` (all optional).

There is deliberately no Connect RPC for dead letters yet. The console
cannot query this data until a backend endpoint exists; that endpoint is
part of the deferred UI work, not of 2.1. Suggested RPC shape when built:

- `ListDeadWork(kind, limit)` → records as above (payload as opaque JSON
  string; never add per-kind columns to the RPC).
- `ReenqueueWork(dedup_key, kind)` → bool enqueued (resurrect semantics).
- Authorization: platform operators only.

## Acceptance criteria for the future UI work

- An operator can list dead and failed records with kind, resource, attempts,
  sanitized error, and timestamps without database access.
- An operator can re-enqueue a dead record and observe it return to pending
  and get claimed.
- Non-operators cannot see or re-enqueue dead letters.
- Queue lag is charted or at least visible next to the dead list.
- No per-kind queue tables or endpoints are reintroduced: one list, kind as
  a filter.
