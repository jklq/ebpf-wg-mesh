# Frontend handoff — 2.7a xDS control plane and Caddy cutover

Backend-only delivery. The control plane is now the xDS authority for a
single Envoy instance: it serves a versioned LDS/CDS/EDS/RDS snapshot over
ADS, Envoy ACK/NACK is the apply protocol, and Caddy is gone from the
production path, localteststack, and the VM harness. No console UI was
added or changed.

## What landed

- `internal/controlplane/xds` owns snapshot computation, serving, and
  publication. `Build` derives listeners, routes, EDS clusters, and
  endpoints deterministically from healthy backends plus static routes.
  Only ready, non-draining `serving` allocations are routed. Snapshots are
  consistency-checked before serving.
- `xds.Server` serves ADS (plus per-type SotW), tracks per-node applied
  versions and NACKs, seeds reconnecting nodes, and retains
  last-known-good on NACK.
- `xds.Publisher` implements `PlatformIngress` (`Sync`/`RequestSync`/
  `Converged`). Publication is written by the lease owner through
  compare-and-swap on `version`; every replica runs `Follow`/`Replicate`
  and serves the durable publication from its own xDS socket.
- Subscriber apply state is durable (`xds_node_observations`), registered
  at first contact before any config is served. A rollout moves a
  withdrawn allocation to `Draining` only once every known Envoy has fully
  applied the current snapshot.
- Control-plane config: `ingress.xdsListen`
  (`CONTROLPLANE_INGRESS_XDS_LISTEN` / `--ingress-xds-listen`, default
  `127.0.0.1:18000`). SDS is served but empty until 2.8 lands
  certificates.
- localteststack runs `envoyproxy/envoy:v1.36-latest` with an ADS-only
  bootstrap rendered by `xds.RenderBootstrap`.
- VM harness subscribes `cmd/xds-probe` to both replicas' xDS ports.

## Deferred

- Ingress status surface (published version, per-Envoy applied revisions,
  NACK counts) — 2.7b/2.8.
- Config-diff-without-secrets view for rollouts — 2.7b.
- Availability policy for instances that never come back — 2.7b.
