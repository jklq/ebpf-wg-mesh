# Frontend handoff — 2.7a xDS control plane and Caddy cutover

Backend-only delivery. The control plane is now the xDS authority for a
single Envoy instance: it serves a versioned LDS/CDS/EDS/RDS snapshot over
ADS, Envoy ACK/NACK is the apply protocol, and Caddy is gone from the
production path, localteststack, and the VM harness. No console UI was
added or changed.

## Backend delivered

- `internal/controlplane/xds` owns snapshot computation, serving, and
  publication. `Build` derives listeners, route table, EDS clusters, and
  endpoints deterministically from healthy backends plus static routes;
  the version is the hex SHA-256 of the canonical inputs, so racing
  replicas produce identical bytes. Only ready, non-draining
  `serving` allocations are routed; draining/withdrawing allocations
  leave EDS as soon as the state flips, before the container is
  destroyed. Snapshots are consistency-checked before serving, so a
  rollout never publishes partially.
- `xds.Server` serves ADS (plus per-type SotW) from a snapshot cache,
  tracks per-node applied versions and NACKs, seeds reconnecting nodes
  with the current snapshot, and retains last-known-good on NACK.
- `xds.Publisher` implements the existing `PlatformIngress`
  (`Sync`/`RequestSync`) contract, so every delivery/catalog/deletion
  trigger now republishes xDS. Publication is fenced by the singleton
  lease; the `xds_publications` row records
  `version/hash/counts/publisher/updated_at` via compare-and-swap so
  split ownership converges on identical content.
- Control-plane config replaces the Caddy admin fields with
  `ingress.xdsListen` (`CONTROLPLANE_INGRESS_XDS_LISTEN` /
  `--ingress-xds-listen`, default `127.0.0.1:18000`; production
  requires an explicit host). SDS is served but empty until 2.8 lands
  certificates; Envoy serves plaintext until then. The xDS transport is
  currently plaintext without client auth and must be network-isolated;
  mTLS lands with the fleet work.
- localteststack runs `envoyproxy/envoy:v1.36-latest` with an
  ADS-only bootstrap rendered by `xds.RenderBootstrap` (proven against
  real Envoy: subscribe, ACK on all four types, traffic routed, unknown
  hosts 404).
- The VM harness subscribes an `xds-probe` (`cmd/xds-probe`) to both
  replicas' xDS ports and records the union of hostnames, endpoints,
  and versions in `latest.json` plus every response in `requests.log`.

## Deferred UI

1. An ingress status surface: published xDS version, per-Envoy applied
   revisions, and NACK counts with the latest rejection message. The
   backend source is `xds.Server.Status()`; there is no RPC or console
   view yet, and per-instance health/availability policy is 2.7b's
   scope.
2. A config-diff-without-secrets view for rollouts (2.7b owns the
   availability policy this would explain).

## API contracts (backend)

Go (`internal/controlplane/xds`):

- `Build(BuildInput{Backends, Static, ListenAddrs}) (*Snapshot, error)` —
  deterministic versioned snapshot; `Snapshot{Version, Hash, Counts,
  CacheSnapshot()}`.
- `NewServer(ctx) *Server`; `server.GRPCServer() *grpc.Server` serves
  ADS plus LDS/CDS/EDS/RDS/SDS; `server.Publish(ctx, snap)`;
  `server.Status() Status{Version, Hash, Counts, PublishedAt,
  HasSnapshot, Nodes map[string]NodeStatus}` where `NodeStatus{Applied
  map[typeURL]version, NACKs, LastNACK}`.
- `NewPublisher(PublisherConfig{Source, Publications, Server, Static,
  ListenAddrs, PublisherID, MinSync})` implements
  `delivery.PlatformIngress` plus `Run(ctx)` for the singleton loop.
- `Dial(ctx, addr, nodeID, opts...) (*Client, error)` with
  `Request/Subscribe/Recv/RecvContext/CloseSend/Close` is the minimal
  ADS subscriber shared by tests and `cmd/xds-probe`.
- `RenderBootstrap(BootstrapConfig{NodeID, XDSAddress, AdminAddress})
  (string, error)` renders the ADS-only Envoy bootstrap.
- `(*database).LoadPublication` /
  `CompareAndSwapPublication(oldHash, version, hash, counts,
  publisher)` persist the publication row.

`Server` (`internal/controlplane/server.go`): `XDSAddr()` is the
subscribe address; `XDSServer()` exposes status inspection.

## Acceptance criteria

- A published version reaches a subscribed Envoy on all four types;
  unknown Host headers get 404, never a default backend.
- A NACK is recorded with its message and does not withdraw the
  published snapshot; a fresh subscriber still converges on it.
- A reconnecting Envoy converges on the current version without
  waiting for the next publication.
- Two racing publishers serve byte-identical snapshots and one
  publication-row winner; a fenced stale owner publishes nothing.
- Draining an allocation removes its endpoint from EDS while the
  allocation row still exists.
