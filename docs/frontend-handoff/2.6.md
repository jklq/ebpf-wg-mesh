# Frontend handoff — 2.6 Deploy-by-digest

Backend-only delivery. Runtime identity is now an immutable artifact
pinned to an image manifest digest; mutable tags are user input only and
never run. No console UI was added or changed.

## Backend delivered

- `build_artifacts` is insert-only and records every successful build
  (`kind = build`) and every direct-image deploy (`kind = direct_image`):
  source snapshot digest, commit SHA, build recipe, builder toolchain
  version, image repository + manifest digest, the pinned `image_ref`,
  `source_image_ref` (the user's original input when it was a tag), build
  actor, and timestamps.
- Clean cutover of runtime identity: `deployments`, `deployment_transitions`,
  and `service_rollouts` reference `artifact_id` instead of storing an
  image string; the digest-pinned `artifact.image_ref` is what reaches
  desired state and agents. Existing API `image_digest` / `resolved_image`
  fields now always carry that pinned form.
- Direct-image tags resolve to manifest digests at deploy time via the OCI
  Distribution API (anonymous pull; a registry that demands credentials
  fails closed with an actionable error). A tag that moves after resolution
  never changes what runs; only a fresh release re-resolves it.
- Skip rebuild: when the same source snapshot + build recipe + toolchain
  version already produced an image for the service, no builder work is
  queued and the existing artifact rolls out with the service's current
  variables (deployment `reason_code = BUILD_REUSED`).
- Retention (operator-configurable via
  `CONTROLPLANE_BUILD_ARTIFACTS_RETENTION_DAYS`, default 30, and
  `CONTROLPLANE_BUILD_ARTIFACTS_KEEP_RECENT`, default 20): artifacts
  referenced by a deployment,
  transition, rollout, or the service's current pointer are rollback
  material and never pruned; only unreferenced artifacts age out.
  Keep-recent ranks among the aged-out candidates (the newest ones survive
  regardless of age); unreferenced artifacts inside the retention window
  are never pruned.
- Resolution fails closed on hostile registries: a registry host must be
  a public destination unless the operator allowlists it
  (`CONTROLPLANE_DIRECT_IMAGE_ALLOWED_PRIVATE_REGISTRIES`), auth realms
  stay on the registry's own site, and redirects are refused. Deploy
  errors already surface these refusals as actionable messages; no
  console change is required, though operator-facing error copy may name
  the allowlist flag.

## API contracts (backend)

`PlatformService` (`api/proto/platform.proto`):

- `BuildArtifact{id, service_id, build_id, kind, source_snapshot_digest,
  commit_sha, build_recipe, builder_version, image_repository,
  image_manifest_digest, image_ref, source_image_ref, build_actor_kind,
  build_actor_id, created_at}`. `image_ref` is the digest-pinned runtime
  identity; `source_image_ref` is the user's original input (a mutable tag
  for direct-image deploys) and is display-only. `build_id` is empty for
  `direct_image` artifacts.
- `DeploymentRecord.artifact` and `BuildStatus.artifact` carry the
  artifact behind the deployment/build. The existing `image_digest` /
  `resolved_image` fields equal `artifact.image_ref` and can be replaced
  by it in the UI.
- `ListServiceArtifacts(ListServiceArtifactsRequest{service_id, limit})`
  returns the service's artifacts newest first (default limit 50).
  Service-read authorized; unauthorized callers get `NotFound`/`Internal`
  per the standard read mapping.

Go (`internal/controlplane/delivery`): `ListServiceArtifacts`,
`PruneBuildArtifacts`, `BuildArtifactRecord`, `BuilderToolchainVersion`;
Connect wrappers in `internal/controlplane/connect_services.go`.

## Deferred UI

1. Present `artifact.image_ref` as the deployed image identity everywhere
   (service panel, deployment history, build status) instead of echoing
   the spec's image string. A mutable tag should only ever appear labeled
   as user input (e.g. `nginx:latest → nginx@sha256:…` using
   `source_image_ref` and `image_ref`).
2. Deployments with `status.reason_code = BUILD_REUSED` carry no new
   builder work; surface the existing detail ("Reusing previously built
   image for commit …") as a first-class state distinct from a fresh build,
   and avoid showing empty build progress for them.
3. An artifact provenance view (e.g. on the deployment or a service tab)
   backed by `ListServiceArtifacts`: source snapshot digest, commit,
   recipe, builder version, build actor, created time — and which artifact
   the current deployment and each rollback target will run.

## Acceptance criteria

- Everywhere a running or deployed image is shown, the digest-pinned
  `image_ref` is displayed; the spec's tag appears only as user input next
  to it, never as the identity of what runs.
- A tag moving in the registry changes nothing in the UI until a new
  release resolves it; the previously deployed revision still shows its
  own stored digest and rollback to it shows exactly that digest.
- Reused-image deployments render as "reusing previously built image"
  without pending build steps.
- The provenance view lists artifacts newest first with the fields above,
  and every rollback/exact-redeploy target shows the pinned digest it
  will run before the user confirms.
