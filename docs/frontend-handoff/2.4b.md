# Frontend handoff — 2.4b Hardened build isolation backend

Backend-only delivery. The hardened `hardened` executor, the
containerd sandbox backend, per-execution BuildKit daemons,
data-plane egress enforcement, and content-addressed cache isolation
are implemented and tested. Production refuses the development
executor. No console UI was added or changed.

## Backend delivered

- `internal/builder`: new `hardened` executor behind the canonical
  `BuildExecutor` interface (`Execute`, `RecoverStaleWorkspaces`,
  `Name`, `Isolating` with `Isolating() == true`). Every build step
  (railpack plan, buildctl) runs in a one-shot OCI sandbox: private
  mount/PID/network/IPC/UTS/cgroup namespaces, zero Linux
  capabilities, no-new-privileges, read-only root filesystem, default
  seccomp profile (namespace manipulation denied), masked/readonly
  system paths, deny-all device policy, and only the execution
  workspace (read-only snapshot nested in a writable root), an
  optional content-keyed cache dir, and rendered resolver files
  bind-mounted from the host. Resource limits map to a hard cgroup
  resident-set cap, swap cap, PID cap, and CPU/file-size/process-count
  rlimits; overlay writes are polled and killed past the disk budget,
  and the post-build check accounts the workspace plus the
  per-execution daemon root plus content-cache growth against
  MaxWorkspaceBytes (2.4a counts the workspace only).
- Network policy is enforced at the data plane, not just validated:
  every execution gets a private network namespace that is
  loopback-only when general egress is denied, or CNI-attached
  (operator-provided build network, selected by exact name — never
  the workload mesh) with denied-CIDR blackhole routes otherwise.
  Setup never falls back to host networking.
- Each build gets a per-execution `buildkitd` with an isolated root
  and socket, joined to the execution network namespace, started
  without insecure entitlements, and stopped with the workspace — so
  sibling builds share no daemon cache, worker, or session state. The
  hardened executor ignores the shared BuildKit address and refuses
  `docker` build binaries (ambient buildx state).
- Cache isolation: `builder.cache.mode=content-addressed` mounts a
  host cache dir keyed purely by `ContentCacheKey` (snapshot digest,
  recipe, toolchain) and passes local import/export cache flags; any
  key that does not match the build content is refused before the
  sandbox starts. Mode `none` (default) mounts nothing. Cache dirs
  accumulate under the builder work dir; the operator prunes them.
- `internal/config`: builder configuration carries `sandbox`
  (backend, socket, namespace, image, runtime, snapshotter, CNI
  plugin/conf dirs, CNI network, nameservers, buildkitd binary) and
  `cache.mode`, with defaults, validation, flags, and env vars. The
  executor defaults by profile (production → `hardened`,
  development → `development`); production with
  `executor=development` fails validation, and `builder.New`
  additionally refuses to start that combination. The sandbox OCI
  runtime is operator-selectable (default runc; runsc/Kata work
  through the same seam).
- The builder startup contract now prints `executor_hardened` with no
  `executor_non_isolating` flag. No build behavior, log stream shape,
  or RPC changed: builds still report through the existing build-log
  and build-status paths, and failures (timeout, limit exceeded,
  policy violation, cache refusal, sandbox failure) surface as
  ordinary build failures with messages.
- Adversarial suite (`internal/builder/adversarial_*_test.go`):
  filesystem escape, host socket access, fork bomb, disk exhaustion,
  network denial, and cross-project cache access run as one shared
  case list against both the development host path and the sandbox,
  with documented per-backend expectations. Privileged sandbox cases
  (true fork bomb, denied-CIDR gateway proof) run in the
  `linux-runtime` CI job alongside the agent/firewall suites; they
  skip gracefully without root/containerd/CNI.

## Deferred UI: executor and build-network visibility

There is no per-build UI gap: boundary failures surface as ordinary
build failures with messages through the existing build views. The
deferred surface is operator visibility into builder isolation
posture, extending the 2.4a handoff:

Suggested placement: wherever builder/operator status lands (follow
the 3.10 operator control room when it exists; until then this view
has no home and stays unbuilt). Suggested content per builder:

- executor name (`development` or `hardened`)
- isolating flag (non-isolating renders as an explicit "does not
  isolate untrusted code" warning, not a neutral label)
- sandbox backend and image (hardened only), CNI network name, cache
  mode

## API contracts (backend)

No new RPC was added; none is needed for the deferred view beyond what
already exists:

- Builder startup contract string (`BuilderStartupContract.String()`)
  contains `executor_<name>` and, for non-isolating executors,
  `executor_non_isolating`. It is printed at builder startup and in
  localteststack output.
- `ExecutionSpec`/`ExecutionResult`/`SandboxStep` are in-process Go
  types in `internal/builder`, not wire types. Do not expose them
  directly.

When the operator view is built, back it with a builder-status source
that already exists (health endpoint or control-plane builder record),
not a new per-executor endpoint.

## Acceptance criteria for the future UI work

- An operator can see which executor each builder runs, whether it
  isolates hostile code, and (for hardened) the sandbox image,
  network, and cache mode, without reading builder logs.
- A non-isolating executor is shown as an explicit warning.
- A builder that fails validation (e.g. development executor in
  production, unknown sandbox backend, unconfigured sandbox image)
  surfaces its startup error through the existing builder-status path.
- Build failure, log, and status views are unchanged by this item.
