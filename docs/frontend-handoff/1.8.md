# Frontend handoff — 1.8 Safe deletion

Backend-only delivery. Tombstone lifecycle, typed confirmations, deletion
previews, restores, and background garbage collection are implemented and
tested. The console only gained the regenerated protobuf clients plus one
`toListProjectsRequest` mapper; no delete/restore UI was added or changed.

## Backend delivered

- Delete operations on projects, environments, services, domain bindings,
  and volumes tombstone instead of destroying. The row keeps serving reads,
  new work is refused, ingress and allocations are withdrawn, and a
  garbage-collection loop destroys the row after `delete_expires_at`.
- Grace period is configurable: `controlplane.deletion.gracePeriodDays`
  (default 7, must be > 0), flag `--deletion-grace-period-days`.
- Typed confirmations: project delete always requires `confirmation_name`
  matching the current project name; production-environment delete requires
  the current environment name; volume delete always requires the current
  volume name. Other deletes take no confirmation. Repeats are idempotent
  and never re-check the confirmation.
- Volumes are not recoverable (no restore RPC): deletion is one-way but
  delayed by the grace period. Deleting a volume referenced by a live
  service is refused (`FailedPrecondition`, volume-in-use); deleting a
  production volume that was ever attached is refused (possibly non-empty)
  until the stateful volume provider (06-stateful) owns the data lifecycle.
- Restores clear the resource's own tombstone within the grace period.
  Restoring a child with no tombstone of its own under a deleted parent is
  refused (`FailedPrecondition`, restore top-down). Restoring a collected
  (garbage-collected) resource fails; the row is gone.
- Listings hide tombstones by default; every list request has
  `include_deleted` for recovery/operator flows. Single-resource reads
  return the row with its `DeletionState` (effective state: own tombstone
  or nearest tombstoned ancestor when `inherited` is true).

## Deferred UI

1. **Delete confirmation dialogs** for projects, production environments,
   and volumes: show the deletion preview (dependent environments,
   services, domains, volumes), require typing the current resource name,
   and surface backend `FailedPrecondition` errors (confirmation mismatch,
   volume in use / possibly non-empty) without closing the dialog.
2. **Tombstone visibility and restore actions**: somewhere authorized users
   can list recently deleted projects/environments/services/domains with
   their expiry timestamps and restore them within the grace period.
   Volumes must be shown as non-recoverable (no restore action).
3. **Ingress/workload honesty**: deleted services stop serving immediately
   (before GC). Any console state derived from desired-state snapshots
   already converges; no special casing needed beyond not showing
   tombstoned resources as healthy.

## API contracts (backend, Connect + gRPC, `api/proto/platform.proto`)

Deletes and restores:

- `DeleteProject(project_id, confirmation_name)` → Empty.
  `FailedPrecondition` on confirmation mismatch; managed projects are
  refused by authorization (`PermissionDenied`).
- `RestoreProject(project_id)` → Project.
- `DeleteEnvironment(environment_id, confirmation_name)` → Empty.
  `confirmation_name` required for production only; `FailedPrecondition`
  on mismatch.
- `RestoreEnvironment(environment_id)` → Environment.
- `DeleteService(service_id)` → Empty. No confirmation.
- `RestoreService(service_id)` → Service.
- `DeleteDomainBinding(hostname)` → Empty. No confirmation.
- `RestoreDomainBinding(hostname)` → DomainBinding.
- `DeleteVolume(volume_id, confirmation_name)` → Empty.
  `FailedPrecondition` on confirmation mismatch, volume in use, or
  possibly-non-empty production volume. No restore exists.

Previews (call before showing a confirmation dialog):

- `PreviewProjectDeletion(project_id)` → `DeletionPreview` with
  `environments, services, domains, volumes`.
- `PreviewEnvironmentDeletion(environment_id)` → `DeletionPreview` with
  `services, domains, volumes`.
- `PreviewVolumeDeletion(volume_id)` → `DeletionPreview` with `services`
  (live services referencing the volume; non-empty means deletion will be
  refused) and their `domains`.

Preview element fields: environment `{id, name, is_production}`, service
`{id, name, environment_id, environment_name}`, domain `{hostname,
service_id, service_name, platform_generated}`, volume `{id, name,
environment_id}`.

Listings and resource state:

- `ListProjects(include_deleted)`, `ListEnvironments(project_id,
  include_deleted)`, `ListServices(environment_id, ..., include_deleted)`,
  `ListVolumes(environment_id, include_deleted)`,
  `ListDomainBindings(service_id, include_deleted)`.
- `Project, Environment, Service, Volume, DomainBinding` carry an optional
  `DeletionState deletion` (`deleted_at, deleted_by_user_id,
  delete_expires_at, inherited`). Absent while live.

## Acceptance criteria for the future UI work

- Deleting a project, production environment, or volume shows the
  dependent resources and refuses to proceed until the current name is
  typed exactly.
- A user who just deleted a project, environment, service, or domain can
  find it in the console and restore it before `delete_expires_at`.
- Volumes are never presented as restorable; attempting to delete an
  attached or ever-attached production volume explains why it was refused.
- Default listings never show tombstoned resources; the recovery view is
  the only place they appear.
