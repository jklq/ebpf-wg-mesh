# Frontend handoff — 2.4a Build execution boundary

Backend-only delivery. The `BuildExecutor` seam, the development executor
implementation, explicit per-execution limits, scoped push credentials, and
verified workspace cleanup are implemented and tested. No console UI was
added or changed.

## Backend delivered

- `internal/builder`: every build now runs through the `BuildExecutor`
  interface (`Execute`, `RecoverStaleWorkspaces`, `Name`, `Isolating`).
  The development executor is the only implementation: it extracts a
  re-verified source snapshot into a read-only directory, runs the
  railpack/buildctl steps as host children with an explicit environment
  (no ambient inheritance) and prlimit-backed process limits on Linux,
  scopes the docker config to exactly one push repository, and destroys
  and verifies workspace removal on completion, cancellation, timeout,
  and (via stale-marker recovery at startup) worker death.
- `internal/config`: builder configuration carries `executor`,
  `limits` (timeout, memory, CPU seconds, max file, max processes,
  max workspace bytes), and `network` (general-egress flag, denied
  CIDRs) with defaults, validation, flags, and env vars.
- The builder startup contract now prints `executor_development` and
  `executor_non_isolating`; production startup additionally logs a
  warning that the executor does not isolate untrusted code. No build
  behavior, log stream shape, or RPC changed: builds still report
  through the existing build-log and build-status paths.

## Deferred UI: executor visibility

There is no per-build UI gap: failures from the new boundary (timeout,
limit exceeded, credential scope, cleanup) surface as ordinary build
failures with messages through the existing build views. The only
deferred surface is operator visibility into which executor a builder
runs and whether it isolates hostile code.

Suggested placement: wherever builder/operator status lands (follow
the 3.10 operator control room when it exists; until then this view
has no home and stays unbuilt). Suggested content per builder:

- executor name (today always `development`)
- isolating flag (today always false → render as an explicit
  "does not isolate untrusted code" warning, not a neutral label)

## API contracts (backend)

No new RPC was added; none is needed for the deferred view beyond what
already exists:

- Builder startup contract string (`BuilderStartupContract.String()`)
  contains `executor_<name>` and, for non-isolating executors,
  `executor_non_isolating`. It is printed at builder startup and in
  localteststack output.
- `ExecutionSpec`/`ExecutionResult` are in-process Go types in
  `internal/builder`, not wire types. Do not expose them directly.

When the operator view is built, back it with a builder-status source
that already exists (health endpoint or control-plane builder record),
not a new per-executor endpoint. The hardened executor from 2.4b
will reuse the same contract features with a different name and no
`executor_non_isolating` flag.

## Acceptance criteria for the future UI work

- An operator can see which executor each builder runs without reading
  builder logs.
- A non-isolating executor is shown as an explicit warning, and the
  warning disappears when 2.4b lands without UI changes.
- Build failure, log, and status views are unchanged by this item.
