# Frontend handoff: 2.3b signing-key rotation in the dashboard

Backend landed. The control plane stores and rotates all platform signing
keys (`internal-ca`, `registry`, `user-assertion`, `dashboard-session`)
in `platform_signing_keys`, signs with the active key, and verifies
against active plus retiring through each scope's overlap (runbook and
lifetime table: `docs/signing-keys.md`). Operator rotation is CLI-only
(`controlplane signing-keys init|list|rotate-start|rotate-finish|export|
check|issue-client-cert`); no PlatformService RPC exposes key state, and
no console UI was added. This doc is the contract for the dashboard
remainder: dual-secret verification during HMAC rotation overlap.

## What the backend does (no console work needed)

- ECDSA scopes (`internal-ca`, `registry`) rotate without dashboard code:
  agents renew and adopt the new cluster identity over sync, replicas
  flip server leafs on their own, and the registry trust bundle refreshes
  via `signing-keys export` (operator step in the runbook).
- `user-assertion` verification on the control plane tries the active
  secret first, then the retiring secret, for the full 5-minute overlap.
  Assertions stay 30s max age (`PlatformUserAssertionMaxAgeSeconds`),
  matching the backend's `userAssertionMaxAge`.
- `dashboard-session` material is exported byte-for-byte (no framing) via
  `controlplane signing-keys export --scope dashboard-session [--out
  PATH]` (`--out` uses mode `0600`). The control plane never verifies
  dashboard sessions; it is only the system of record for the secret.
- `issue-client-cert` mints dashboard/builder mTLS client identities from
  the active CA as JSON (`ca_pem_b64`, `cert_pem_b64`, `key_pem_b64`);
  statically provisioned dashboard client certs must be re-issued before
  an `internal-ca` `rotate-finish` (runbook step, operator-owned).

## Console work items

1. Dual-secret session verification. `console/src/lib/dashboard/server.ts`
   currently loads one `DASHBOARD_JWT_SECRET` and the JWT helpers verify
   against it alone. Add an optional predecessor secret (e.g.
   `DASHBOARD_JWT_SECRET_PREVIOUS`, same loader/validation rules:
   required-when-set semantics like `optionalSecret`, never equal to the
   active secret) and verify access/refresh tokens against active first,
   then the predecessor. Sign/refresh always with the active secret.
   Rotation flow: operator runs `rotate-start`, exports the new secret,
   sets it as `DASHBOARD_JWT_SECRET` with the previous value moved to
   the predecessor variable, restarts the dashboard, waits the 31-day
   overlap, runs `rotate-finish`, then clears the predecessor variable.
2. User-assertion secret rollover. The dashboard signs assertions with
   `DASHBOARD_CONTROLPLANE_USER_ASSERTION_SECRET` (must stay >= 32 bytes
   and distinct from `DASHBOARD_JWT_SECRET`). Rotation flow: operator
   runs `rotate-start` (generating or supplying the replacement),
   exports it, swaps the dashboard variable, restarts; the control plane
   verifies both for 5 minutes. No verification change is needed on the
   dashboard (it only signs assertions), but the distinctness validation
   must keep passing across the swap — validate the new pair, not the
   old one.
3. Document both flows in the dashboard runbook section (or link
   `docs/signing-keys.md`): exact variable names, restart points, and
   the overlap waits (5 minutes for user-assertion, 31 days for
   session). Until item 1 lands, `dashboard-session` rotation logs out
   every holder of a refresh token minted under the old secret — say so.
4. Optional, not required by 2.3b: console UI for key status/rotation.
   There is deliberately no RPC for it. If wanted later, the backend
   must first add read-only `ListSigningKeys` (scope, kid, state,
   type, wrapping key, retired-at — never private bytes) and guarded
   rotation mutations to PlatformService; do not shell out to the CLI
   from the console.

## API contract

None. This handoff needs no new RPC: rotation commands run against the
control-plane database, and secrets reach the dashboard through its host
secret manager (env/file), not through PlatformService. Regenerating TS
bindings is not required.

## Acceptance criteria

- `user-assertion` rotation: after `rotate-start` + dashboard secret swap
  + restart, dashboard RPCs keep succeeding with zero
  `Unauthenticated` spike; after the 5-minute overlap + `rotate-finish`,
  RPCs still succeed and the old secret is removed from the host store.
- `dashboard-session` rotation (once item 1 lands): a browser session
  with a refresh token minted before `rotate-start` survives the secret
  swap + dashboard restart and refreshes successfully through the
  overlap; after `rotate-finish` + predecessor removal, new logins work
  and no valid pre-rotation session was dropped mid-overlap.
- `bun run check`, `typecheck`, unit, and integration suites pass; no
  secret value appears in console logs, snapshots, or fixtures.
- The dashboard refuses to start when the predecessor secret equals the
  active secret, with the same `DashboardConfigError` style as the
  existing distinctness checks.
